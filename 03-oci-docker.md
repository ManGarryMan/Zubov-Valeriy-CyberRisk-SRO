# 3. OCI (Open Container Initiative), образы и Docker Engine

## Что такое OCI

Open Container Initiative (OCI) — проект под управлением Linux Foundation, основанный в 2015 году (Docker и другие компании). Цель: открытые стандарты для контейнеров, чтобы образ, собранный одним инструментом, запускался любым другим совместимым.

OCI определяет три спецификации:

|   Спецификация    | О чём |
|-------------------|-----------------------------------------------------------------------------------------|
|     Image Spec    | формат образа контейнера: слои, манифест, конфигурация                                  |
|   Runtime Spec    | как запускать контейнер из распакованного образа (конфиг `config.json`, жизненный цикл) |
| Distribution Spec | API реестра образов: как загружать (push) и скачивать (pull)                            |

Эталонная реализация Runtime Spec — runc.

## Контейнер и виртуальная машина

- ВМ эмулирует железо, внутри своя ОС со своим ядром.
- Контейнер — обычный процесс (или группа процессов) на хосте, изолированный средствами ядра Linux. Ядро общее с хостом.

Поэтому контейнеры легче и быстрее стартуют, но изоляция слабее, чем у ВМ: уязвимость ядра затрагивает все контейнеры.

Изоляция строится на:
- namespaces — изолируют представление системы: pid, net, mnt, uts, ipc, user, cgroup;
- cgroups — ограничивают ресурсы (CPU, память, I/O);
- capabilities — дробят привилегии root на отдельные права;
- seccomp — фильтр системных вызовов;
- AppArmor / SELinux — обязательный контроль доступа.

## Что такое образ (image)

Образ — неизменяемый (read-only) шаблон, из которого запускаются контейнеры. Содержит файловую систему приложения (бинарники, библиотеки, конфиги) и метаданные (команда запуска, переменные окружения, порты).

### Из чего состоит образ по OCI Image Spec

- Слои (layers) — tar-архивы с изменениями файловой системы. Каждый слой хранит только разницу с предыдущим.
- Конфигурация (config) — JSON: архитектура, ОС, ENV, ENTRYPOINT/CMD, история слоёв, список хешей слоёв.
- Манифест (manifest) — JSON: перечисляет конфиг и слои с их размерами и **digest** (хеш).
- Index (image index) — необязательный список манифестов для разных платформ (amd64, arm64) — «мультиархитектурный» образ.

Все объекты адресуются по содержимому (**content-addressable**): идентификатор = `sha256:` хеш содержимого. Это даёт проверку целостности: подмена слоя изменит хеш.

### Как образ собирается

Основной способ — Dockerfile: текстовый файл с инструкциями. Пример:

```dockerfile
FROM python:3.12-slim

WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY . .

USER 1000
EXPOSE 8000
CMD ["python", "app.py"]
```

Что происходит при `docker build`:
1. Берётся базовый образ (`FROM`).
2. Каждая инструкция, меняющая файловую систему (`RUN`, `COPY`, `ADD`), создаёт новый слой.
3. Инструкции вроде `CMD`, `ENV`, `EXPOSE`, `USER` меняют метаданные конфига.
4. Результат упаковывается в слои + конфиг + манифест.
5. Слои кэшируются: если инструкция и её входные данные не менялись, слой берётся из кэша. Поэтому редко меняющиеся шаги (установка зависимостей) ставят выше часто меняющихся (копирование кода).

Слои складываются в единую файловую систему через union filesystem (в Docker по умолчанию `overlay2`): нижние слои read-only, сверху тонкий слой записи у запущенного контейнера (copy-on-write).

### Multi-stage build

Позволяет собрать приложение в одном образе, а в финальный перенести только результат. Итоговый образ меньше и содержит меньше лишнего (а значит, меньше поверхность атаки):

```dockerfile
FROM golang:1.22 AS build
WORKDIR /src
COPY . .
RUN CGO_ENABLED=0 go build -o /app

FROM gcr.io/distroless/static
COPY --from=build /app /app
USER nonroot
ENTRYPOINT ["/app"]
```

### Инструменты сборки

Dockerfile — формат, не привязанный к одному инструменту. Образы по OCI собирают также BuildKit (современный движок сборки в Docker), Buildah, Kaniko, Podman build.

### Реестры образов

Образы хранятся в реестрах (registry): Docker Hub, GitHub Container Registry (ghcr.io), Quay, частные реестры. Формат API — OCI Distribution Spec. Полное имя: `registry/репозиторий:тег` или `...@sha256:digest`. Тег — изменяемая метка (`latest` может указывать на разные образы), digest — неизменяемый идентификатор.

## Docker Engine: архитектура

Docker Engine — клиент-серверное приложение. Основные части:

```
 docker CLI ──REST API──▶ dockerd ──▶ containerd ──▶ containerd-shim ──▶ runc ──▶ контейнер
   (клиент)        (демон Docker)   (высокоуровневый   (держит процесс)   (низкоуровневый
                                      runtime)                             runtime, OCI)
```

### Docker CLI
Команда `docker`. Сама ничего не запускает: преобразует команды (`docker run`, `docker ps`) в вызовы API демона.

### Docker API
REST API демона `dockerd`. По умолчанию доступен через Unix-сокет `/var/run/docker.sock`, опционально через TCP (порт 2375 без TLS, 2376 с TLS). Через API можно управлять контейнерами, образами, сетями, томами.

Пример вызова напрямую:
```bash
curl --unix-socket /var/run/docker.sock http://localhost/containers/json
```

Безопасность: доступ к сокету или к открытому TCP-порту API равен root-доступу на хосте (можно запустить привилегированный контейнер с монтированием `/`). Поэтому:
- не открывать API наружу без TLS и аутентификации;
- не монтировать `docker.sock` внутрь контейнеров без крайней необходимости;
- членство в группе `docker` фактически даёт права root.

### dockerd
Демон Docker. Принимает запросы API, управляет образами, сетями, томами, сборкой; делегирует запуск контейнеров в containerd.

### containerd
Высокоуровневый container runtime (проект CNCF). Управляет жизненным циклом контейнеров: загрузка и хранение образов, снапшоты файловой системы, запуск контейнеров через низкоуровневый runtime. Используется и отдельно, например в Kubernetes.

### containerd-shim
Небольшой процесс-посредник между containerd и контейнером. Позволяет перезапускать containerd/dockerd, не убивая работающие контейнеры, и держит stdio и код возврата.

### runc (runtime)
Низкоуровневый runtime, эталонная реализация OCI Runtime Spec. Читает `config.json` и создаёт контейнер: настраивает namespaces, cgroups, capabilities, seccomp и запускает процесс. После запуска runc завершается. Альтернативы: crun, youki, а для усиленной изоляции gVisor (runsc) и Kata Containers.

### Docker proxy
Термин используется в двух смыслах, и в отчёте стоит различать:
1. docker-proxy (userland proxy) — процесс, который Docker запускает для проброса портов (`-p 8080:80`). Перенаправляет трафик с порта хоста в контейнер. Основную работу при этом обычно делают правила iptables/nftables (NAT), а docker-proxy нужен для отдельных случаев, например обращения с localhost хоста. Отключается опцией `userland-proxy: false` в `daemon.json`.
2. Прокси для доступа в интернет / к реестру — настройки `HTTP_PROXY`/`HTTPS_PROXY` для демона (при сборке и pull образов) и для контейнеров.

Также встречается socket proxy (например, tecnativa/docker-socket-proxy) — прослойка, которая ограничивает, какие методы Docker API доступны клиенту.

### Runtime (на что обратить внимание)
В схеме два уровня runtime:
- высокоуровневый (containerd, CRI-O): образы, снапшоты, жизненный цикл;
- низкоуровневый (runc, crun): непосредственно создание изолированного процесса.

Контейнеры по умолчанию запускаются от root внутри контейнера, что повышает риски при побеге; лучше использовать непривилегированного пользователя и rootless-режим.

## Основные команды

```bash
docker pull nginx:1.27              # скачать образ
docker images                       # список образов
docker build -t myapp:1.0 .         # собрать образ из Dockerfile
docker run -d -p 8080:80 nginx      # запустить контейнер
docker ps                           # запущенные контейнеры
docker logs <id>                    # логи
docker exec -it <id> sh             # зайти в контейнер
docker stop <id> && docker rm <id>  # остановить и удалить
docker history myapp:1.0            # слои образа
docker inspect myapp:1.0            # метаданные (JSON)
docker save -o myapp.tar myapp:1.0  # выгрузить образ в tar (OCI-слои)
```

## Безопасность контейнеров (кратко)

- Минимальные базовые образы (alpine, distroless), меньше пакетов — меньше уязвимостей.
- Запуск от непривилегированного пользователя (`USER`), rootless Docker/Podman.
- Не запускать `--privileged`, убирать лишние capabilities (`--cap-drop ALL`).
- Не хранить секреты в образе и в слоях: они остаются в истории слоёв.
- Фиксировать версии образов (тег или лучше digest), не полагаться на `latest`.
- Сканировать образы на уязвимости (Trivy, Grype, Docker Scout).
- Подписывать образы (cosign / Sigstore), проверять источник.
- Ограничивать ресурсы (`--memory`, `--cpus`) и использовать read-only файловую систему (`--read-only`).
- Регулярно обновлять ядро хоста и Docker.
